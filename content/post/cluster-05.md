### 集群概述  

---

#### 一. 集群技术的定义  
集群是由多台互联的独立服务器（节点）构成的系统级架构，通过分布式协同机制实现单一系统映像（SSI），其技术本质包含：

- 资源聚合：将离散的硬件资源（CPU/内存/存储）抽象为统一服务池。  
- 服务虚拟化：对外呈现单一入口（如虚拟IP或域名），屏蔽内部节点细节。  
- 容错与自治：支持节点故障时服务自愈与任务重调度。 

简单一句话描述：一组协同工作但对外表现为一个整体的服务器组叫做集群 

##### 1.1 核心价值  
| 特性     | 技术内涵                                                     |
| -------- | ------------------------------------------------------------ |
| 高性能   | 通过并行计算突破单机性能瓶颈（如100+节点并行渲染）。         |
| 高可用   | 实现99.999% SLA（全年停机<5分钟），依赖故障检测-隔离-恢复三阶段机制。 |
| 弹性扩展 | 支持线性扩展比（如吞吐量随节点数线性增长），适应突发流量或计算需求。 |

##### 1.2 应用场景  
| 场景                | 技术需求                                                                 | 典型工具/协议                            |
|---------------------|-------------------------------------------------------------------------|----------------------------------------|
| Web服务集群      | 高并发请求分发、会话保持、动态扩缩容                                       | Nginx、LVS、Keepalived、HAProxy            |
| 数据库集群       | 数据强一致性、读写分离、主从同步                                           | Redis Sentinel、Redis Cluster、keepalived |
| 科学计算(了解) | 大规模矩阵运算、跨节点通信优化、任务分片、如：分布式渲染（特效、建模）             | MPI（OpenMPI）、Slurm                 |

#### 二. 集群基础概念  

##### 2.1 核心组件  
| 组件     | 功能描述                      | 技术细节                                                     |
| -------- | ----------------------------- | ------------------------------------------------------------ |
| 计算节点 | 执行实际业务逻辑的物理/虚拟机 | - 节点间时钟同步（NTP）<br>- 资源隔离（cgroups/namespace）   |
| 调度器   | 全局资源分配与任务路由        | - 集中式调度（如LVS Director）<br>- 分布式调度（如Consul服务发现） |
| 共享存储 | 提供全局一致的数据访问视图    | - 块存储（iSCSI SAN）<br>- 文件存储（NFS）                   |

##### 2.2 性能扩展方式  
| 扩展方式            | 操作方式 | 适用场景                                | 局限性                                  |
|---------------------|---------------------|---------------------------------------|---------------------------------------|
| 垂直扩展        | 升级单节点硬件（CPU/内存） | 单任务资源需求高（如内存数据库）          | 硬件成本指数增长，存在物理上限（如CPU核数，内存插槽数） |
| 水平扩展        | 增加节点数量（更经济高效） | 高并发、无状态服务（如Web服务器）         | 需要解决数据分片与一致性难题              |

```bash
垂直扩展：增加服务器的硬件性能(增加和更换硬件)
    缺点：
        1、需要停止业务运行
        2、性价比低
        3、依然有瓶颈(无法无限扩展)
    优点：
        1、不需要重新部署
        2、不需要重新更新网站结构

水平扩展：增加服务器的数量来进行并行处理
    缺点：
        1、需要重新部署多台服务器
        2、重新规划网站结构（可扩展）
    优点：
        1、性价比较高
        2、扩展瓶颈较低
```

#### 三. 集群分类与架构  

##### 3.1 负载均衡集群（LBC）  

**技术定义**

负载均衡（Load Balancing Cluster） 是一种网络技术，旨在通过将用户请求或工作任务动态分摊到多个服务器或操作单元上，实现资源的优化利用、提高系统性能及可靠性。

```bash
1. 基本定义
   - 扩展带宽与吞吐量：通过多节点并行处理，突破单点性能瓶颈。
   - 提升可用性：避免单节点过载或故障导致服务中断，保障业务连续性。
   - 增强灵活性：支持动态扩容或缩容，适应流量波动。

2. 核心原理
   负载均衡基于流量调度器（如硬件设备或软件模块）实现请求分发，具体流程如下：
    
   请求接收：客户端访问统一入口（如虚拟IP或域名）。
   策略匹配：根据预设算法（如轮询）选择目标服务器。
   流量转发：将请求分发至选中的服务器，并可能修改网络层或应用层信息（如IP地址、HTTP头）。
   健康检查：实时监测后端服务器状态，自动剔除故障节点，确保服务可用性。 
```

**节点类型和层级划分**

```bash  
# 节点类型
   - 调度器节点：请求接受和任务调度分配
   - 应用服务节点：处理调度器分配的具体任务
   - 一致性存储节点：保证各个应用节点数据的一致性

# 实现层级  
1. 二层（数据链路层）：
   - 协议：LACP（动态链路聚合控制协议）
   - 工具：支持此协议的网络设备或服务器设备
   - 特点：需要双端设备都支持LACP协议，适用于高带宽需求场景，如数据中心内部网络互联。
   
2. 四层（传输层）+ 三层（网络层）：  
   - 协议：IP、TCP/UDP  
   - 工具：LVS（IPVS内核模块）、HAProxy（tcp模式）  
   - 特点：高性能（仅解析IP包头）数据库负载均衡  

3. 七层（应用层）：  
   - 协议：HTTP/HTTPS、gRPC  
   - 工具：Nginx（upstream模块、proxy_pass模块）
   - 特点：支持内容路由（如URL路径）

# 实现方式
1. 硬件：
   - 网络设备：路由器、交换机等
   - 专业硬件：
     F5公司：	Big ip 系列产品
     A10公司： Thunder系列产品
     
2. 软件：
   - 四层：LVS
   - 七层：Nginx
```

**算法类型**

```bash
# 调度算法  
1. RR（轮询算法）
   - 原理：像轮流值日一样，按顺序把请求依次分配给每台服务器，不管服务器当前是否忙碌。例如：A、B、C三台服务器，请求会按A→B→C→A→B→C循环分配。
   - 特点：简单公平，但可能导致性能差的服务器堆积请求。比如B处理慢，但RR依然会继续给它分配新请求，导致B越来越忙。

2. WRR（加权轮询算法）
   - 原理：在RR基础上给服务器“加权重”，权重高的服务器分到更多请求。例如：A权重1，B权重2，则分配顺序可能是B→B→A→B→B→A（具体顺序由算法决定）。
   - 特点：适合服务器性能不均衡的场景。比如用高性能服务器（权重高）处理更多请求，低性能的少处理。

3. SH（源地址哈希算法）
   - 原理：根据用户的IP地址分配服务器，同一个IP的请求永远发给同一台服务器。比如用户甲的IP经过哈希计算后固定由服务器B处理。
   - 特点：解决会话保持问题（如登录状态），但可能导致同一IP的大量请求压垮一台服务器（比如学校共用IP的场景）。

4. LC（最少连接算法）
   - 原理：动态选择当前连接数最少的服务器，像超市排队时选人最少的收银台。例如：A有10个活跃连接，B有5个，新请求会优先给B。
   - 特点：实时调整，但未考虑服务器性能差异（可能把请求分给性能差但连接少的服务器）。

5. WLC（加权最少连接算法）
   - 原理：结合服务器权重和连接数，优先选“（连接数+1）/权重”最小的服务器。
     例如：A权重3，连接数2；B权重1，连接数1。计算后A的值是(2+1)/3=1，B是(1+1)/1=2，选A。
   - 特点：既考虑性能差异，又兼顾实时负载，是LVS默认算法。

# 总结：  
   - 静态算法：（RR、WRR、SH）适用于服务器性能已知且稳定的场景。  
   - 动态算法：（LC、WLC）更适合实时负载波动大的环境。  
   - 实际选择需结合业务需求，例如需要会话保持用SH，需高性能均衡用WLC。
```

##### 3.2 高可用集群（HAC）  

**定义：**高可用性（High Availability, HA）指系统通过设计减少服务中断时间，确保在预定期限内持续提供服务的能力。其核心目标是保障业务连续性，即在故障或维护期间，用户感知的服务中断时间最小化甚至为零，如：通过冗余节点+故障转移机制，实现服务连续性保障。

```bash
心跳检测（Heartbeat Detection）是一种通过周期性发送信号（心跳包）来验证网络连接或设备状态的机制，广泛应用于维持长连接、监控系统健康以及保障服务可用性。

- 实现方式：
  多播（如Corosync）、单播（如Keepalived UDP单播）  

- 检测频率：
  毫秒级（如10ms超时+3次重试）  
```

**脑裂：**在高可用性（HA）系统中，脑裂现象（Split-Brain）是指由于节点间通信中断，导致原本统一的集群分裂为多个独立子集群，各子集群认为自身是唯一有效的主节点，进而引发资源争抢、数据不一致甚至服务中断的严重问题。

```bash  
# 解决方案：
   - 冗余线路：配置多种心跳路径（如以太网+串行线）
   - 仲裁策略：
     - 多数派投票（如3节点集群需2票确认）
     - 参照对象：设置参考IP地址，争抢之前先判断参考IP的连通性，通则争抢，不通则不抢。
   - STONITH：物理级断电（如IPMI硬重启故障节点）  # Shoot The Other Node In The Head
```
**相关指标**

```bash
1. MTTF（Mean Time To Failure，平均无故障时间）
   - 定义：系统无故障运行的平均时间，通常用于衡量系统的可靠性。例如，若某设备 MTTF 为 10,000 小时，表示平均每运行 10,000 小时后可能发生一次故障。
   - 适用场景：适用于不可修复的系统（如一次性设备），或用于预测可修复系统的故障频率。

2. MTTR（Mean Time To Recovery，平均恢复时间）
   - 定义：从故障发生到系统完全恢复所需的平均时间，包括故障发现、定位和修复的全过程。
   - 作用：衡量系统的可维护性。MTTR 越短，系统可用性越高。  
   - 公式关联：可用性（Availability）= MTTF / (MTTF + MTTR)。例如，若 MTTF 为 1000 小时，MTTR 为 1 小时，则可用性为 99.9%。
    99% 		87.6h
    99.9%		8.8h
    99.99%		53m
    99.999%		5m
    # 还有一种算法MTBF / (MTBF + MTTR),基本没有区别

3. RTO（Recovery Time Objective，恢复时间目标）
   - 定义：灾难发生后，业务系统从中断到恢复服务可接受的最长时间。例如，若 RTO 为 1 小时，则必须在 1 小时内恢复服务。
   - 应用：指导灾难恢复策略设计（如主备切换、集群部署）。RTO 越短，成本越高（需实时热备、自动化切换）。
   - 与 MTTR 的区别：MTTR 是多次故障的平均恢复时间，而 RTO 是单次故障允许的最大恢复时间目标。

4. RPO（Recovery Point Objective，恢复点目标）
   - 定义：灾难发生时允许丢失的最大数据量，通常以时间衡量。例如，若 RPO 为 1 小时，则最多允许丢失 1 小时内的数据。
   - 应用：决定数据备份频率（如每 5 分钟备份一次）。RPO 越短，需实时同步数据（如数据库双写、日志复制）。
   - 核心挑战：高 RPO 要求（如金融交易系统需 RPO=0）需牺牲存储成本和性能。

5. 实际案例
   - 数据库备份：若每 24 小时备份一次，故障后需 5 分钟重启恢复，则 RTO=5 分钟，RPO=24 小时。  
   - 多活架构：通过异地多活集群实现 RTO≈0、RPO≈0，但需高昂成本。
通过平衡这些指标，企业可在可靠性、成本和业务连续性间找到最优解。
```

| 指标 | 关注点         | 应用领域     | 典型值示例               |
| ---- | -------------- | ------------ | ------------------------ |
| MTTF | 系统可靠性     | 硬件寿命预测 | 10,000 小时              |
| MTTR | 系统可维护性   | 运维优化     | 1 小时（需快速修复）     |
| RTO  | 业务中断容忍度 | 灾难恢复设计 | 金融系统 RTO ≤ 5 分钟    |
| RPO  | 数据丢失容忍度 | 数据备份策略 | 支付系统 RPO=0（零丢失） |

#### 四. 名词解释-扩展

##### 1. Session 

```bash
Session（会话）是服务器端用于跟踪用户状态的机制。当用户首次访问服务器时，服务器会创建一个唯一的 Session ID，并在内存或数据库中存储与该用户相关的数据（如登录信息、购物车内容等）。Session 解决了 HTTP 协议无状态的问题，确保用户在多次请求中保持连续性。  

核心特点： 
- 存储位置：数据存储在服务器端，客户端仅保存 Session ID（通常通过 Cookie 传递）。  
- 安全性：敏感信息（如用户身份）存储在服务器，客户端无法直接篡改。  
- 生命周期： 
  - 会话级：用户关闭浏览器或超时（默认约 20-30 分钟）后失效。  
  - 持久化：可通过配置延长有效期（如 24 小时）。  

工作原理： 
1. 创建：用户首次访问时，服务器生成 Session ID 并存储相关数据。  
2. 传递：Session ID 通过 Cookie 或 URL 参数（如 `?PHPSESSID=xxx`）传递到客户端。  
3. 验证：后续请求中，服务器通过 Session ID 检索用户数据，维持会话状态。  
```

##### 2. Cookie 
```bash
Cookie 是服务器发送到客户端（浏览器）的小型文本文件（通常小于 4KB），用于记录用户身份、偏好等非敏感信息。客户端在后续请求中自动携带 Cookie，帮助服务器识别用户。 

核心特点： 
- 存储位置：数据存储在客户端（浏览器内存或硬盘）。 
- 限制： 
  - 单个域名下最多存储约 20 个 Cookie，总大小不超过 4KB。 
  - 客户端可禁用或清除 Cookie，导致功能受限。 
- 生命周期： 
  - 会话级：关闭浏览器后失效（未设置 `Expires` 参数）。 
  - 持久级：设置 `Expires` 或 `Max-Age` 后长期有效（如 30 天）。 

工作原理： 
1. 设置：服务器通过 HTTP 响应头 `Set-Cookie` 发送键值对（如 `username=Alice`）。 
2. 携带：浏览器在后续请求的 `Cookie` 头中自动附加相关数据。 
3. 管理：客户端可通过 JavaScript 或浏览器设置管理 Cookie。 
```

##### 3. Session 与 Cookie 的区别 
| 维度         | Session                          | Cookie                     |
|------------------|------------------------------|---------------------------|
| 存储位置     | 服务器端（内存/数据库）    		| 客户端（浏览器）          |
| 数据类型     | 任意对象（用户信息、状态等）     | 仅字符串（键值对）           |
| 安全性       | 高（数据不暴露给客户端）        | 低（可能被窃取或篡改）        |
| 生命周期控制 | 由服务器配置超时时间            | 由客户端或服务器设置过期时间   |
| 性能影响     | 占用服务器资源，大规模用户时需优化 | 无服务器负担，但传输增加带宽消耗 |

##### 4. PV（Page View）

```bash
定义：页面浏览量
   用户每次打开或刷新页面即计为一次 PV，用于衡量网站页面的总访问次数。例如，同一用户连续刷新页面 5 次，PV 将累计为 5 次。
特点：
   与用户数量无关：仅反映页面被访问的总次数，可能与实际用户数差异较大（如单个用户反复刷新）。
应用场景：
   评估页面内容吸引力或活动效果，如电商促销页面的点击热度。
```

##### 5. UV（Unique Visitor）

```bash
定义：独立访客
   统计周期内（通常为 24 小时）访问网站的独立用户数。基于 Cookie 或设备标识区分用户，同一用户多次访问仅计为 1 次。
特点：
   依赖 Cookie 或设备标识：若用户清除 Cookie 或更换设备，会被计为新 UV。
   与 IP 的关系：同一 IP 可能对应多个 UV（如家庭网络多设备访问），而同一用户更换 IP 仍可能被计为同一 UV。
应用场景：
    衡量网站的真实用户规模，如新用户增长分析。
```

##### 6. IP（Internet Protocol）

```bash
定义：独立 IP
   统计周期内访问网站的独立 IP 地址数量。同一 IP 多次访问仅计为 1 个。
特点：
   局限性：局域网用户（如公司、学校）共享公网 IP 时，多个用户访问仅计为 1 个 IP。
   真实性较高：常用于粗略估算用户地理分布。
对比 UV：
   IP 无法区分同一网络下的不同用户，因此 UV 通常更准确反映真实用户数。
```

##### 7. PV/UV/IP 指标间的关系与对比

| 指标 | 核心差异 | 典型场景 |
|----------|--------------|--------------|
| PV vs UV | PV 统计页面访问量，UV 统计用户数量 | 活动页 PV 高但 UV 低，说明用户反复刷新但未吸引新用户。 |
| UV vs IP | UV 基于用户标识，IP 基于网络地址 | 公司网络（同一 IP）多人访问，UV 大于 IP。 |
| VV vs PV | VV 统计会话次数，PV 统计页面刷新次数 | 用户一次会话浏览 5 页，计为 1 次 VV 和 5 次 PV。 |
