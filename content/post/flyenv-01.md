## 一、先说痛点

我是一名运维/实施工程师，日常在 Windows 笔记本上干活。工作内容不算复杂：写 Python 运维脚本、用 Node 跑一些辅助工具、同时本地还想跑 MySQL 和 Redis，用来搭 Zabbix、K8s 的练习环境。

听起来需求挺简单的，但真做起来问题一堆：

- 一个老脚本依赖 Python 3.9，新写的工具要用 3.12。系统里装了两个版本之后，PATH 一乱就开始互相打架，`pip install` 装到哪个版本全靠运气；
- Node 也是，公司项目跑 18，自己练手的想用 20；
- 想本地起个 MySQL 练建库，又懒得每次翻配置文件；
- 笔记本内存吃紧，Docker Desktop 一开，风扇直接起飞，续航砍半。

环境配置这件事，我前后折腾了差不多两年多，换了三种方案，最后才找到顺手的。

## 二、我试过的三种方案

### 1. 系统直装

最直接，也最脏。

装第二个 Python 的时候开始踩坑：PATH 里谁排在前面、`pip` 指向哪个解释器、系统里某些工具依赖老版本又不敢动。最后机器上留了一堆删不干净的残留，重装系统的心都有了。

### 2. pyenv + nvm

命令行党最熟悉的组合。能用，但有几个问题：

- Windows 上体验明显不如 macOS/Linux，`nvm-windows` 和原版 `nvm` 基本是两套东西，命令都不完全一样；
- 切换靠手敲命令，忘了切就报错，而且报错信息通常看不出真正原因；
- 只管语言版本，数据库、Redis、Nginx 这些还是得单独折腾。

### 3. Docker Desktop

隔离干净，环境一致性最好，这也是它最大的优点。

但对我这种需求来说：

- 内存占用大，空跑就吃掉 2G 以上；
- 启动慢，改个配置文件经常要重建容器；
- 只是想「跑一个干净的 Python 3.12」的时候，套一层容器虚拟化太厚了。

不是说 Docker 不好，是我的场景配不上它。

## 三、换成 FlyEnv 之后

FlyEnv 的思路和上面三个都不一样：**它不做虚拟化，也不接管你的系统 PATH，而是把每个运行时当成一个可以独立开关的模块。**

我现在用它管这些东西：

| 模块 | 用途 | 装的版本 |
|---|---|---|
| Python | 写运维脚本 | 3.9 + 3.12 共存 |
| Node.js | 辅助工具、脚本 | 18 + 20 共存 |
| MySQL | 练 Zabbix 建库 | 8.0 |
| Redis | 练缓存和队列 | 7.x |
| Nginx | 本地验证配置 | 最新稳定版 |

真正让我留下来的是这几个点：

**1. 多版本共存，进目录自动切换**

每个项目目录配好自己的语言版本，`cd` 进去自动生效，不用手敲 `nvm use` 或者 `pyenv local`。对我这种「一会儿改老脚本、一会儿写新工具」的节奏来说特别友好 —— 最大的收益是**不再需要记住自己当前在哪个版本上**。

**2. 原生二进制，没有虚拟化开销**

不跑容器、不开虚拟机，服务启动是毫秒级。最直接的体感是笔记本风扇不叫了，续航回来了。同样一套 Python + MySQL + Redis，FlyEnv 占的内存比 Docker Desktop 低一个数量级。

**3. 服务统一面板**

MySQL、Redis、Nginx 的启停、日志、配置文件入口都在一个界面里。查日志不用再翻目录，端口冲突会直接可视化提示 —— 这个对运维出身的排查习惯来说很顺手，因为端口占用问题本来就是高频故障点。

**4. 本地域名 + 自动 HTTPS**

写 `myapp.test` 这样的本地域名，一键配好，证书也自动签发。以前改 hosts 加自签证书要折腾十几分钟，现在是点两下的事。

**5. 顺手的小工具集**

Base64 编解码、JSON 格式化、正则测试、时间戳转换、SSL 证书生成、URL 解析 —— 这些我原来都是开浏览器找在线工具站的，现在内置了，而且**数据不出本机**。处理日志里带敏感信息的片段时，这一条比方便更重要。

## 四、需要说清楚的边界

FlyEnv 不是万能的，有几点必须讲明白，不然容易误导人：

- **它替代不了 Docker。** 本地日常开发、单体应用、语言和数据库版本管理，FlyEnv 很合适；但复杂微服务编排、需要复刻生产容器网络拓扑的场景，还是得用 Docker。两个是共存关系，不是二选一。
- **社区版有 3 个本地站点的限制。** 但核心运行时（Python / Node / Java / PHP 等）和数据库模块是不限量的。如果你跟我一样，本地站点需求不多，这个限制基本碰不到。
- **它是给本地开发用的。** 不要拿它跑生产环境，生产该用正经的服务器部署或容器化方案。

## 五、谁适合，谁不适合

**适合：**

- 笔记本开发，内存吃紧、不喜欢 Docker 的重量级方案
- 同时要维护多个语言版本的项目
- 主要做单体应用、本地服务调试
- 想少花时间在环境配置上的人

**不适合：**

- 需要本地复刻生产 K8s / 微服务拓扑的
- 团队已经统一用容器化工作流的

## 六、总结

我现在的流程是：装完 FlyEnv，勾选需要的模块，点安装，把项目目录绑上去，直接开始写代码。整个流程大概三五分钟，而且换电脑之后能快速还原。

回头看这段折腾史，从系统直装到 pyenv/nvm 到 Docker Desktop 再到 FlyEnv，本质是在找**「刚好够用的那层抽象」**：

- 太薄了（系统直装），东西会互相打架；
- 太厚了（Docker Desktop），机器资源先被吃掉一半；
- FlyEnv 刚好卡在中间 —— 有隔离、能切版本、又足够轻。

工具没有绝对的好坏，只有和你的场景配不配。如果你也在被环境配置反复消耗时间，可以试试。
