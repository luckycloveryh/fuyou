MySQL 视图、外键、存储过程与主从复制

介绍《MySQL 视图、外键、存储过程与主从复制》，涵盖数据库存储过程与事务相关、MySQL存储引擎与特性和MySQL运维管理等实践要点。

2025/12/30 · 8873 字 · -- 次阅读

一、数据库存储过程与事务相关

  1. 存储过程语法与事务控制
    • 讲解创建存储过程（proc）的基本语法，需定义名称、参数，在begin和end之间编写核心语句。
    • 强调事务在存储过程中的应用：需通过start transaction开启事务，执行SQL语句后，根据执行结果用commit（成功）或rollback（失败）结束事务。
    • 介绍通过变量（如timas）控制事务走向，结合exception异常捕捉机制，若捕获到sql exception，将变量值从0改为1，最终依据变量值判断事务提交或回滚。
  2. 事务ACID特性
    • 原子性（A）：事务中的SQL操作是一个整体，要么全部成功，要么全部失败，不存在部分执行的情况。
    • 一致性（C）：事务运行过程中，数据库数据始终保持一致状态，基于前一步操作结果执行后续操作，最终要么全量改变数据库，要么不改变。
    • 隔离性（I）：多个事务可同时运行且互不干扰，隔离性通过隔离级别区分，共分为四个级别。
    • 持久性（D）：事务提交后，对数据库的修改会永久保存，即使系统故障也不会丢失。
  3. 事务隔离级别
    • 读未提交（Read Uncommitted）：一个事务可读取另一个未提交事务的数据，安全性低，可能导致“脏数据”问题（如领导未确定的涨薪数据被提前读取）。
    • 读已提交（Read Committed）：一个事务只能读取另一个已提交事务的数据，解决了脏数据问题，但可能出现“不可重复读”（如查询余额后，未还款时余额被他人扣减，再次查询结果不一致）。
    • 可重复读（Repeatable Read）：通过加锁（如排他锁），保证同一事务内多次读取同一数据结果一致，在事务未结束前，其他事务无法修改该数据，MySQL默认采用此级别。
    • 串行化（Serializable）：事务完全串行执行，一个事务结束后另一个才开始，安全性最高，但效率极低，适用于对数据一致性要求极高且并发量低的场景。

二、MySQL存储引擎与特性

  1. 存储引擎特性
    • 介绍InnoDB存储引擎的核心特性，包括支持外键（foreign key）、事务、行级锁（Row-level Locking），而MyISAM等存储引擎不支持这些特性。
    • 对比行级锁与表级锁：行级锁仅锁定操作的单行数据，其他行可正常操作，效率高；表级锁锁定整个表，其他事务无法操作表中任何数据，效率低。
  2. 存储引擎切换
    • 若当前存储引擎（如MyISAM）不支持事务等特性，可将默认存储引擎改为InnoDB，6.9及以上版本部分环境默认存储引擎为InnoDB，低版本（如部分5.x版本）默认是MyISAM，需手动修改配置切换。

三、MySQL运维管理

  1. 用户管理
    • 用户创建与授权：可通过两条SQL语句分别创建用户（如create user '李四'@'%' identified by '123';）和授权（如grant select, insert on db2.* to '李四'@'%';），也可合并为一条语句直接完成创建并授权。
    • 用户分类：按登录位置分为本地用户（登录地址为localhost）和远程用户（登录地址为具体IP或%，允许任意地址登录）；按权限分为普通用户和管理员（如root），管理员拥有所有权限，普通用户权限需手动授予。
    • 密码管理
      • 初始化密码：创建用户时直接指定，或对已存在用户（如root）通过alter user 'root'@'localhost' identified by '123';初始化。
      • 修改密码：管理员可通过alter user或set password修改所有用户密码；普通用户仅能通过set password = password('新密码')修改自身密码，且需调用密码加密函数处理明文密码。
      • 忘记密码解决：普通用户需联系管理员重置；管理员忘记密码时，需修改MySQL配置文件（如my.cnf），添加skip-grant-tables跳过权限验证，重启服务后无密码登录，刷新权限（flush privileges）并重置密码，最后删除配置文件中跳过权限的语句并重启服务。
  2. 数据备份与恢复
    • 备份方法
      • 文件拷贝：直接拷贝MySQL数据目录（如/var/lib/mysql）下的文件，适用于简单场景，但备份文件为二进制格式，无法直接查看内容。
      • mysqldump命令：通过命令将数据库或表备份为SQL脚本文件，可指定备份的库（如mysqldump -u root -p123 db3 > db3_backup.sql）或表（如mysqldump -u root -p123 db3 student > student_backup.sql），备份文件包含表结构（drop table if exists、create table）和数据（insert语句），便于查看和管理。
    • 恢复方法
      • 若备份文件未指定数据库，恢复时需先指定目标数据库（如mysql -u root -p123 db3 < db3_backup.sql），或在备份文件中添加use 数据库名;语句。
      • 恢复过程本质是执行备份文件中的SQL语句，若恢复时目标表已存在，可通过drop table if exists语句先删除原表再重建，避免报错。

四、后续运维方向

视频最后提及基础部分结束后，后续将讲解MySQL运维进阶内容，包括数据预研、主从复制、代理配置等服务级别的配置与管理，以及日常工作中对MySQL服务的全面管理要点（如数据安全、用户权限控制、备份策略制定）。

五、视图、外键、存储过程与事务（新增知识点）

（一）视图（View）

  1. 概念：将经常使用的复杂查询语句封装成一张可视化的虚拟表，其封装的是查询语句而非结果，数据会随原表变化而变化。
  2. 创建语法： 
    create view 视图名 as 查询语句;
    查询语句通常为连表查询等复杂语句，可给表或列起别名。
  3. 使用方法：像使用普通表一样，通过： 
    select 列名 from 视图名;
    查询数据。
  4. 查看与删除：通过： 
    show create view 视图名;
    查看视图创建语句；删除视图使用： 
    drop view 视图名;
  5. 特点：方便频繁使用复杂查询，不存储数据，仅保存查询逻辑，MySQL中的user表在部分版本中是视图而非普通表。

（二）外键（Foreign Key）

  1. 概念与作用：属于表间约束，是一张表中的列（可为非主键），其取值需来自另一张表的关联列的取值范围，用于约束表与表之间的数据关系，保证数据完整性。
  2. 特点：一张表可有多个外键，可加在单列或多列上，与唯一键有相似之处。
  3. 创建语法： 
    alter table 表名 add constraint 外键名 foreign key (当前表列名) references 另一张表名(另一张表列名);
    创建时需注意数据符合约束要求，否则创建失败。
  4. 约束影响：
    • 查询：主表和副表查询不受影响。
    • 新增：副表新增数据时，外键列值需在主表关联列取值范围内。
    • 删除：副表删除数据不受影响；主表若有数据被副表外键引用，则无法直接删除。
    • 修改：副表修改外键列值，需在主表关联列取值范围内；主表若数据被副表引用，无法直接修改该数据。
  5. 删除外键：需先删除外键关联关系，再删除外键索引，语法分别为： 
    alter table 表名 drop foreign key 外键名;
alter table 表名 drop index 外键名;

（三）存储过程（Procedure）

  1. 概念：MySQL中的自定义函数，将多条SQL语句（如增删改查语句）封装在一起，实现特定功能，可多次调用。
  2. 创建语法： 
    create procedure 存储过程名() begin SQL语句; end;
    小括号不可省略，用于区分变量名与存储过程名。
  3. 调用方法：通过： 
    call 存储过程名();
    调用。
  4. 特点：可批量执行SQL语句，但语句间无事务关系，若一条语句报错，后续语句不再执行，已执行成功的语句结果会保留。

（四）事务（Transaction）

  1. 概念：将一组SQL语句当作一个整体（最小单元，不可再分）处理，保证数据一致性。
  2. 四大特性（ACID）：
    • 原子性（Atomicity）：事务中的语句要么全部执行，要么全部不执行。
    • 一致性（Consistency）：事务运行过程中不改变数据库原始数据，语句基于前一条语句的效果执行。
    • 持久性（Durability）：事务执行成功并提交后，对数据的修改永久有效；若执行失败，数据回滚到初始状态。
    • 隔离性（Isolation）：未明确提及具体内容，但属于事务核心特性之一。
  3. 操作流程：
    • 开启事务：通过： 
      begin;
      或： 
      start transaction;
      开启。
    • 执行SQL语句：在事务中执行所需的SQL语句。
    • 提交事务：若所有语句执行成功，通过： 
      commit;
      提交事务，数据修改生效。
    • 回滚事务：若有语句执行失败，通过： 
      rollback;
      回滚事务，数据恢复到事务开启前状态。
  4. 演示效果：开启事务后执行删除操作，查询时数据显示已删除，执行回滚后数据恢复；若提交事务，数据删除效果永久保留。

六、数据库备份与还原操作（新增知识点）

（一）多库备份与单库备份的区别及操作

  1. 多库备份
    • 需使用特定参数：备份多个数据库时，需在命令中添加 -B（或 --databases）选项；若需备份所有数据库，可使用 -A（或 --all-databases）选项。若不添加 -B 选项，直接指定多个库名，系统会误将后续库名当作第一个库的表，导致备份失败。
    • 备份文件特点：备份文件中会包含创建数据库（若不存在则创建）、切换数据库及操作对应表的命令，还原时无需额外指定目标库，直接还原即可。
  2. 单库备份
    • 备份文件特点：仅包含表的相关操作，还原时需手动指定目标库名，否则无法正确还原到对应数据库。
  3. 还原测试场景与操作
    • 测试环境搭建：当需要进行还原测试时，可额外搭建一个MySQL服务作为测试环境，将备份文件通过 SCP 命令传输到测试服务器指定目录。
    • 还原验证：还原完成后，通过查询数据库表数据（如查询用户表、学生表等），对比源库与目标库数据是否一致，以此验证还原效果。

（二）表结构与表数据的单独备份

  1. 相关参数
    • -d（或 --no-data）：仅备份表结构，不包含表数据，备份文件中只有表的创建语句（CREATE TABLE）。
    • -t（或 --no-create-info）：仅备份表数据，不包含表结构，备份文件中只有数据插入语句（INSERT）。
  2. 应用场景：若仅误删除表数据，无需重新运行表结构备份文件，直接使用表数据备份文件恢复即可；若表被删除，则需先运行表结构备份文件重建表，再运行表数据备份文件恢复数据。

（三）条件备份操作

通过 --where 选项可实现按条件备份数据，例如备份 DB3 数据库中 student 表内1990年出生的学生数据，需在备份命令中指定字段条件（如 --where="birthday >= '1990-01-01' AND birthday <= '1990-12-31'"）。备份文件仅包含符合条件的表结构（若未指定单独备份数据）和数据，可灵活满足特定数据备份需求。

七、数据库日志管理（新增知识点）

（一）日志类型及功能

  1. 通用查询日志（General Log）
    • 记录内容：以SQL语句格式记录客户端所有操作，包括连接数据库、创建库表、增删改查（含错误操作）等，可直接通过 vim、tail 等命令查看日志文件内容。
    • 开启方式：需修改MySQL配置文件（如 /etc/my.cnf.d/mysql-server.cnf），添加 general_log = ON 开启日志，并可指定 general_log_file 定义日志文件名及存储路径，默认与数据文件存放在同一目录。
  2. 二进制日志（Binary Log）
    • 记录内容：以二进制格式记录影响数据变化的操作（如增、删、改），不记录查询操作（SELECT），日志文件占用空间较小，但无法直接查看，需使用 mysqlbinlog 命令解析。
    • 开启方式：在配置文件中添加 log-bin = 日志文件名（如 log-bin = mysql-bin），开启后会生成日志文件（如 mysql-bin.000001）及对应的索引文件。
    • 还原应用：还原时可通过指定日志文件的起始字节偏移量（start-position）和结束字节偏移量（stop-position），精准恢复特定时间段或特定操作的数据，可将解析出的SQL语句输出到文件或通过管道直接传入数据库执行还原。
  3. 慢查询日志（Slow Query Log）
    • 功能：默认关闭，开启后可记录执行时间超过指定阈值（如3秒）的SQL语句，用于定位影响系统性能的慢查询，辅助优化（如添加索引）。
    • 配置方式：在配置文件中设置 slow_query_log = ON 开启日志，通过 long_query_time 定义慢查询时间阈值，并指定 slow_query_log_file 定义日志存储路径。
  4. 中继日志（Relay Log）
    • 功能：主要用于主从同步，从库的IO线程会将主库的二进制日志复制到本地并存储为中继日志，SQL线程再读取中继日志并在从库执行，实现数据同步，无需手动开启，主从同步时自动生成。

（二）日志查看与应用示例

  • 通用查询日志：操作数据库（如创建库 new、建表 t、插入数据）后，通过： 
    tail -f 通用日志文件名
    可实时查看操作记录，若表被误删，可从日志中复制建表、插入数据的SQL语句恢复。
  • 二进制日志：使用： 
    mysqlbinlog 二进制日志文件名
    可解析日志，查看操作对应的字节偏移量，例如从偏移量497到932的操作包含建表和插入数据，可通过： 
    mysqlbinlog --start-position=497 --stop-position=932 日志文件名 | mysql -u root -p
    直接还原该段操作的数据。

八、MySQL自增参数与字符集配置（新增知识点）

（一）自增相关参数

  • 通过： 
    show variables like '%auto_increment%';
    可查看自增参数，包括 auto_increment_increment（自增步长，默认1）和 auto_increment_offset（自增起始值，默认1），可根据需求修改这两个参数调整自增规则。

（二）字符集配置

  • MySQL存在多级别字符集设置，包括服务级、库级、表级、字段级及连接字符集，可通过修改配置文件调整服务级字符集，也可在创建库、表时单独指定字符集（如 CREATE DATABASE 库名 CHARACTER SET utf8mb4），确保支持中文等特殊字符存储。

九、MySQL主从同步搭建（新增知识点）

（一）搭建前提与准备

  1. 需两台MySQL服务器（主库和从库），主库需开启二进制日志，从库需确保与主库初始数据一致（若主库已有数据，需先将主库数据备份并还原到从库）。
  2. 主库与从库的 server-id 必须不同（默认均为1），需在配置文件中分别设置（如主库 server-id=11，从库 server-id=12），修改后重启MySQL服务生效。

（二）搭建步骤

  1. 主库配置
    • 创建同步用户：在主库中创建远程同步用户（如 sync_user），并授予 REPLICATION SLAVE 权限，允许从库通过该用户访问主库二进制日志，命令示例： 
      CREATE USER 'sync_user'@'%' IDENTIFIED BY '123';
GRANT REPLICATION SLAVE ON *.* TO 'sync_user'@'%';
    • 查看主库日志信息：执行： 
      show master status;
      查看主库当前使用的二进制日志文件名（如 mysql-bin.000001）及起始偏移量（如370），记录该信息用于从库配置。
  2. 从库配置

    • 配置主从关系：在从库中执行命令，指定主库地址、同步用户、密码、日志文件名及起始偏移量，命令示例：

      CHANGE MASTER TO MASTER_HOST='192.168.111.2', MASTER_USER='yh',MASTER_PASSWORD='123', MASTER_LOG_FILE='jojo-bin.000001', MASTER_LOG_POS=327;

    • 启动从库线程：执行：

      start slave;

      启动从库的IO线程和SQL线程，通过：

      show slave status\G;

      查看线程状态，若 Slave_IO_Running 和 Slave_SQL_Running 均为 Yes，则主从关系搭建成功。

（三）同步验证

主库中对数据进行操作（如向 new 库的 t 表插入数据 INSERT INTO t VALUES (2, 'Windows');），从库中查询该表数据，若能看到新增数据，说明主从同步正常，从库成功通过IO线程获取主库二进制日志，再通过SQL线程执行日志中的操作，实现数据同步。

十、备份计划与注意事项（新增知识点）

  • 定时备份：需定期执行备份操作（如通过定时任务），但需注意定时任务的执行间隔，若间隔1分钟，需避免在这1分钟内插入数据后未备份就删除，否则数据可能丢失。
  • 日志与备份结合：二进制日志可作为增量备份的补充，结合全量备份文件和二进制日志，可实现更精准的数据恢复，例如全量备份后通过二进制日志恢复后续新增或修改的数据。
